# Поток миграций

## Текущий подход

Проект теперь использует SQL-миграции из директории `migrations/`, а не развивает схему только через runtime-блоки `ALTER TABLE`.

## Как это работает

1. `DatabaseManager` открывает соединение с SQLite.
2. `SchemaInitializer` запускает `MigrationRunner`.
3. `MigrationRunner` гарантирует наличие таблицы `schema_migrations`.
4. Все `*.sql` файлы из `migrations/` применяются в отсортированном порядке.
5. Применённые версии сохраняются в `schema_migrations`.

## Текущие миграции

- `0001_initial_schema.sql`
  - создаёт `users`
  - создаёт `game_saves`
  - создаёт `leaderboard`
  - включает актуальные колонки `account_level` и `dungeon_clears`

## Правила для новых миграций

- Добавлять новый файл с монотонно растущим префиксом, например `0002_add_xyz.sql`
- По возможности делать миграции идемпотентными
- Не редактировать уже применённые миграции задним числом в production-подобных средах
- Предпочитать новую миграцию, а не добавление нового runtime schema patching

## Локальное поведение

Runner выполняется автоматически во время bootstrap приложения, поэтому текущий локальный сценарий запуска остаётся совместимым с существующим проектом.
