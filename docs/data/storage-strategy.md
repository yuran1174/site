# Стратегия хранения игровых данных

## Контекст

Документ фиксирует текущее и целевое решение по хранению данных после введения миграций и persistence-слоя. Решение опирается на фактическую схему `users`, `game_saves`, `leaderboard`, а также на поведение `GameSaveService`.

## Текущее состояние

### `users`

- Хранится в отдельной таблице `users`.
- Содержит identity и auth-данные: `id`, `username`, `password_hash`, `created_at`, `last_seen`.
- Используется как account-level сущность, не как контейнер игрового прогресса.

### `game_saves`

- Хранится в таблице `game_saves`.
- На пользователя приходится одна строка.
- Основной прогресс хранится в `save_data TEXT` как JSON blob.
- `updated_at` фиксирует время последнего server-side upsert.

### `leaderboard`

- Хранится в отдельной таблице `leaderboard`.
- Это не исходный save, а денормализованная проекция для быстрых чтений.
- Сейчас там живут поля:
  - `username`
  - `total_loc`
  - `prestige_count`
  - `account_level`
  - `dungeon_clears`

### Security и runtime-данные

- Security/audit события пишутся в `storage/logs/security.log` в JSONL-формате.
- Rate limit хранится в файловом runtime-слое `storage/ratelimits/`.
- Эти данные не являются игровым save и не должны смешиваться с пользовательским прогрессом.

## Решение по крупным сущностям

### 1. Игровой save idle-ядра

Текущее решение: оставить основной игровой прогресс в JSON внутри `game_saves.save_data`.

Обоснование:

- Данные сильно завязаны на клиентскую модель и содержат много мелких коллекций (`buildings`, `upgrades`, `achievements`, `prestigeShop`, `story`).
- Структура save часто меняется как игровая модель, а не как стабильная бизнес-сущность.
- Для текущего масштаба проекта одна строка save на пользователя проще и дешевле в сопровождении, чем ранняя нормализация десятков таблиц.
- Уже существует server-side нормализация через `GameSaveService`, что уменьшает риск произвольной формы JSON.

Что остаётся в JSON:

- текущее количество ресурсов и прогресса ранa: `loc`, `totalLoc`, `locThisRun`
- счётчики активности: `totalClicks`, `eventCount`, `maxOffline`
- коллекции игрового состояния: `buildings`, `upgrades`, `achievements`, `prestigeShop`, `story`
- meta-поля save: `prestige`, `prestigePoints`, `totalPrestigePoints`, `lastSave`, `version`

Ограничение:

- `save_data` остаётся write-optimized blob, но неудобен для аналитики, массовых выборок и строгой серверно-авторитативной логики.

### 2. Leaderboard и публичные агрегаты

Текущее решение: хранить leaderboard-поля отдельно в таблице `leaderboard` и продолжать считать её производной проекцией от save.

Обоснование:

- leaderboard читается чаще, чем требуется полный save;
- сортировка по `total_loc` и выдача account-level данных не должны требовать чтения и декодирования JSON по всем пользователям;
- часть данных leaderboard уже вычисляется на сервере в `GameSaveService::updateLeaderboard()`.

Что должно жить в отдельных колонках leaderboard:

- ресурсы и метрики, по которым делаются сортировки или публичные списки;
- поля, которые нужны страницам вроде `leaderboard.php` и `profile.php` без полного decode save.

Текущее решение по полям:

- `total_loc` оставить в таблице;
- `prestige_count` оставить в таблице;
- `account_level` оставить в таблице как серверно рассчитанный агрегат;
- `dungeon_clears` оставить в таблице, потому что это и мета-прогресс, и leaderboard-friendly показатель.

### 3. Auth и account metadata

Текущее решение: все auth/account-поля хранить только в `users`.

Обоснование:

- это стабильная реляционная сущность;
- эти данные не относятся к игровому save;
- по ним нужны точечные выборки и обновления.

Что не должно попадать в JSON save:

- `username`
- `password_hash`
- `created_at`
- `last_seen`

### 4. Security/audit logs

Текущее решение: не хранить security/audit события в `game_saves` и не смешивать их с leaderboard.

Обоснование:

- это append-only служебные записи, а не состояние игрока;
- у логов другой срок жизни, другой доступ и другой формат использования;
- хранение таких событий внутри save усложнит расследование инцидентов и раздует игровой blob.

Практическое решение сейчас:

- baseline security logging остаётся файловым в `storage/logs/security.log`.

Следующий шаг при росте проекта:

- вынести audit/security события в отдельную таблицу или отдельное хранилище append-only типа `security_events`.

### 5. Analytics events

Текущее решение: не хранить продуктовую аналитику внутри `game_saves.save_data`.

Обоснование:

- события аналитики имеют событийную, а не state-based природу;
- аналитика требует append-only модели, временных меток, фильтрации и агрегаций;
- запись аналитики внутрь save приведёт к постоянному раздутию JSON и конфликту ответственности.

Рекомендация:

- когда будет выполняться `TASK-035`, вводить отдельную event-схему, а не добавлять analytics в игровой blob;
- минимальный вариант: отдельная таблица `analytics_events`;
- более взрослый вариант: отдельное внешнее event-хранилище после выхода за пределы SQLite.

## Что пока не нужно выносить из JSON

Ниже поля, которые сейчас лучше оставить в `save_data`, пока не появится явная серверная механика или аналитическая потребность:

- `buildings`
- `upgrades`
- `achievements`
- `prestigeShop`
- `story`
- `eventCount`
- `maxOffline`
- `locThisRun`

Причина:

- они используются как часть игрового snapshot-состояния;
- не участвуют в текущих cross-user выборках;
- их нормализация сейчас увеличит сложность сильнее, чем даст пользу.

## Кандидаты на будущую нормализацию

Ниже перечислены сущности, которые стоит вынести в отдельные таблицы только при появлении конкретного драйвера:

### `player_progress_snapshots` или расширение `game_saves`

Когда нужно:

- если потребуется история сохранений;
- если потребуется rollback или расследование порчи save;
- если появится серверная reconcile-логика между несколькими клиентами.

### `player_rewards` или `reward_events`

Когда нужно:

- если minigame и dungeon будут развиваться как независимые системы;
- если потребуется отдельный аудит выдач наград;
- если reward flow станет серверно-авторитативным.

### `player_achievements`

Когда нужно:

- если достижения понадобятся для выборок по конкретным достижениям;
- если потребуется вручную поддерживать/исправлять достижения отдельно от полного save;
- если achievements станут частью аналитики или live-ops механик.

### `player_buildings` / `player_upgrades`

Когда нужно:

- если экономику idle-игры начнут считать на сервере;
- если потребуется дешёвый partial update без перезаписи всего save blob;
- если размер `save_data` начнёт заметно расти.

## Правила принятого решения

1. Реляционно хранить account identity, leaderboard и служебные инфраструктурные данные.
2. Игровой snapshot одного игрока пока хранить в одном JSON blob.
3. Не смешивать state, logs и analytics в одном хранилище.
4. Нормализовать данные только там, где уже есть реальный read/query/audit driver.
5. Любое новое вынесение из JSON оформлять миграцией и обновлением этого документа.

## Границы применимости решения

Это решение подходит для текущего этапа проекта:

- один основной save на пользователя;
- SQLite как основная БД;
- limited backend authority;
- небольшой набор cross-user чтений.

Предположение:

- документ исходит из того, что `game_saves` остаётся canonical save record до тех пор, пока проект не перейдёт к более серверно-авторитативной модели прогресса. Если эта модель появится, стратегию нужно будет пересмотреть вместе с `TASK-021` и `TASK-016`.
