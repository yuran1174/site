# SQLite vs PostgreSQL

## Контекст

Сейчас проект работает на SQLite:

- `config/database.php` по умолчанию указывает `driver=sqlite` и путь `db/game.sqlite`;
- `DatabaseManager` открывает соединение через DSN `sqlite:...`;
- миграции и runtime SQL сейчас ориентированы на SQLite-first запуск;
- основной игровой прогресс хранится как один JSON blob в `game_saves.save_data`, а `leaderboard` и `users` покрывают только ограниченный набор реляционных чтений.

Этот документ фиксирует решение на текущем этапе и критерии, когда SQLite перестаёт быть достаточным вариантом.

## Короткое решение

Текущее решение: оставить SQLite как основную БД на текущем этапе проекта.

Почему:

- проект всё ещё работает как один небольшой PHP-runtime без отдельной БД-инфраструктуры;
- схема данных пока компактная и состоит из `users`, `game_saves`, `leaderboard`, `schema_migrations`;
- для локальной разработки SQLite даёт нулевой overhead по запуску, резервированию портов и DevOps;
- текущая серверная модель не делает тяжёлых cross-user аналитических запросов;
- большая часть игрового состояния хранится как save snapshot по одному пользователю, а не как набор сильно связанных таблиц.

Но:

- инфраструктура ещё не готова к реальному переключению драйвера;
- PostgreSQL не нужен немедленно, но должен стать плановым следующим шагом при росте нагрузки и данных.

## Текущее фактическое состояние

### Что уже хорошо подходит SQLite

- один файл БД без отдельного сервиса;
- простые auth-операции;
- upsert одного save на пользователя;
- небольшие leaderboard-чтения;
- локальный запуск и тесты.

### Что уже ограничивает SQLite-подход

- `DatabaseManager` фактически жёстко привязан к `sqlite:` DSN, несмотря на наличие `DB_DRIVER` в конфиге;
- SQL использует SQLite-специфику вроде `strftime('%s','now')`;
- rate limits и security logs уже живут в файловом runtime-слое, а не в БД;
- продуктовая аналитика ещё не введена, поэтому вопрос write-heavy event ingestion пока просто отложен;
- текущий save-blob удобен для snapshot-хранения, но плохо подходит для будущих аналитических и reconcile-сценариев.

## Сравнение для этого проекта

### SQLite

Плюсы:

- минимальная сложность эксплуатации;
- идеален для локальной разработки и pet/small-project стадии;
- простая резервная копия на уровне файла;
- хорошо подходит для read-light и moderate-write сценария с одной инстанцией приложения.

Минусы:

- слабее масштабируется по конкурентным записям;
- плохо подходит для нескольких параллельных application instances;
- неудобен для тяжёлой аналитики и фоновых обработчиков;
- сложнее строить безопасный production backup/restore без дисциплины вокруг файла;
- путь к high-write event storage у SQLite ограничен значительно сильнее, чем у PostgreSQL.

### PostgreSQL

Плюсы:

- лучше выдерживает конкурентные записи и multiple workers;
- естественнее подходит для event tables, audit trails и аналитических выборок;
- даёт зрелые инструменты бэкапов, репликации и operational monitoring;
- удобнее для постепенной нормализации данных из save-blob в отдельные таблицы;
- лучше подходит для будущего server-authoritative progression.

Минусы:

- выше DevOps-стоимость и требования к окружению;
- сложнее локальный onboarding;
- для текущего объёма проекта это может быть преждевременной инфраструктурой.

## Decision record

### Решение сейчас

1. SQLite остаётся основной production/dev БД на текущем этапе.
2. Новые миграции и документы нужно писать так, чтобы переход на PostgreSQL оставался возможным, но не притворяться, что он уже поддержан.
3. До перехода нельзя добавлять архитектурные допущения, требующие нескольких параллельных writer-инстансов.

### Что это означает practically

- текущая production-модель должна предполагать один основной application instance;
- новые write-heavy подсистемы нужно вводить осторожно;
- продуктовую аналитику нельзя бесконтрольно складывать в текущий SQLite-файл без отдельной оценки нагрузки;
- при появлении server-side economy или event ingestion стратегию нужно пересматривать немедленно.

## Когда SQLite ещё нормален

SQLite остаётся разумным вариантом, пока одновременно верны следующие условия:

- приложение работает как один веб-инстанс;
- основная запись это upsert одного save на пользователя, а не поток событий;
- leaderboard ограничен простыми выборками;
- объём security log и analytics ещё не вынесен в БД;
- нет постоянной конкуренции нескольких процессов за частые записи в одни и те же таблицы;
- бэкап файла БД и ручное операционное сопровождение ещё реалистичны.

## Триггеры обязательного перехода на PostgreSQL

Переход становится обязательным, если выполняется хотя бы один из следующих сценариев.

### 1. Concurrency pressure

- появляется больше одного production application instance;
- появляются background workers, cron-процессы или отдельные consumers, регулярно пишущие в ту же БД;
- возникают lock/contention проблемы на save/reward/auth write path.

Последствие:

- SQLite становится архитектурным узким местом, а не просто удобной локальной БД.

### 2. Write-heavy event storage

- вводится реальная продуктовая аналитика с append-only событиями;
- в БД начинают храниться reward events, audit events или история сохранений в значимом объёме;
- число записей в БД растёт в первую очередь из-за событий, а не из-за single-row save upsert.

Последствие:

- файл SQLite начинает использоваться не по его сильной стороне, и стоимость чтения/архивации/обслуживания резко растёт.

### 3. Server-authoritative gameplay

- сервер начинает сам считать экономику, прогрессию или выдачу наград;
- требуется частичное обновление множества игровых сущностей вместо перезаписи одного save blob;
- появляется необходимость в транзакционных multi-table операциях как в штатном игровом потоке.

Последствие:

- текущая SQLite + save-blob схема перестаёт быть достаточно гибкой и наблюдаемой.

### 4. Production backup and recovery pressure

- нужен регулярный backup без заметного operational риска;
- требуется более надёжный restore/point-in-time discipline;
- инциденты с повреждением файла БД или ручным копированием становятся реальной угрозой.

Последствие:

- файловая operational model уже не соответствует требованиям проекта.

### 5. Analytics/query pressure

- нужны регулярные продуктовые выборки по периодам, сегментам, событиям или cohort-анализу;
- leaderboard перестаёт покрывать все cross-user чтения;
- требуется много служебных или продуктовых read-моделей поверх исторических данных.

Последствие:

- SQLite начинает тормозить не только запись, но и саму возможность развивать продукт.

## Что нужно сделать до перехода

Переход на PostgreSQL не сводится к смене DSN. Перед ним нужно подготовить проект.

### 1. Развязать инфраструктуру от SQLite-first assumptions

Нужно:

- сделать `DatabaseManager` реально driver-aware;
- убрать SQLite-specific SQL из runtime и миграций либо ввести диалектный слой;
- пересмотреть места с `strftime('%s','now')` и похожими выражениями.

### 2. Зафиксировать минимальную PostgreSQL-совместимость схемы

Нужно:

- проверить типы колонок и значения по умолчанию;
- описать миграцию начальной схемы под PostgreSQL;
- зафиксировать правила для JSON/JSONB, timestamps и upsert-паттернов.

### 3. Развести operational и runtime данные

Нужно:

- не тащить rate limit, security logs и будущую аналитику обратно в основной save storage;
- заранее определить, что будет храниться в PostgreSQL как transactional data, а что отдельно как logs/events.

### 4. Подготовить миграционный сценарий

Нужно:

- экспортировать `users`, `game_saves`, `leaderboard` из SQLite;
- загрузить данные в PostgreSQL;
- провести smoke-check на auth/save/load/leaderboard;
- только после этого переключать runtime.

## Рекомендуемый момент перехода

Практическая рекомендация для этого проекта:

- не переходить на PostgreSQL прямо сейчас;
- перейти до внедрения полноценной продуктовой аналитики в БД или до запуска нескольких production instances;
- не начинать server-authoritative progression поверх SQLite, если это создаст регулярные multi-writer и event-heavy сценарии.

Иными словами:

- текущий этап: SQLite остаётся;
- следующий инфраструктурный рубеж: PostgreSQL вводится перед фазой growth, live analytics и более серьёзной серверной логики, а не после того, как SQLite уже начал мешать в production.

## Итог

Решение:

- SQLite подходит проекту сейчас;
- PostgreSQL обязателен не по календарю, а по нагрузочному и архитектурному триггеру;
- ключевой trigger для обязательного перехода: multiple writers, event-heavy storage, server-authoritative progression или серьёзные production-требования к backup/restore.

Предположение:

- документ исходит из того, что проект продолжает жить как single-instance PHP-приложение на ближайшем этапе. Если планируется быстрый выход в multi-instance окружение, решение нужно пересмотреть раньше.
