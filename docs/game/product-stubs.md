# Продуктовые заглушки и решения

## Задача

В продукте не должно быть ссылок или состояний, которые обещают игроку систему, которой фактически нет. Это ломает trust и делает прогрессию визуально богаче, чем она есть на самом деле.

## Найденные заглушки

### 1. `pvp.php`

Факт:

- в проекте нет файла `pvp.php`
- при этом в продуктовой документации и UI арена фигурирует как будущая активность
- раньше прогресс-экран idle выдавал ссылку на `pvp.php` после `prestige >= 3`

Проблема:

- это misleading navigation
- игрок получает ложный unlock и упирается в несуществующую страницу

Решение:

- убрать ссылку на `pvp.php` из runtime UI до реальной реализации страницы
- оставить арену только как planned feature с пометкой `В разработке`
- сохранить продуктовый порог `prestige 3` как будущий gating rule, но не показывать его как доступный контент

Статус:

- принято
- в UI runtime ссылка скрыта

### 2. «Особые события» как отдельная активность

Факт:

- в idle UI был слот активности, который выглядел как отдельный режим
- по факту в продукте нет отдельной event-системы, есть только встроенные случайные события ранa

Проблема:

- игроку обещается отдельная feature surface, которой нет
- смешиваются run events и будущие seasonal events

Решение:

- переименовать в UI будущую сущность в `Сезонные события`
- показывать её как planned layer, а не как уже существующую активность
- текущие случайные события считать частью idle-ядра, а не отдельной страницей

Статус:

- принято

## Что не считать заглушкой

### Dungeon

- страница существует
- вход рабочий
- награда интегрирована в общий прогресс

### Minigame

- страница существует
- награда интегрирована в общий прогресс

### Сюжет

- это не отдельная missing page, а встроенный слой прогрессии

## Принцип на будущее

Новая активность может появиться в пользовательской навигации только если соблюдены все условия:

- существует реальная surface: страница, модалка или встроенный режим
- есть завершённый unlock/entry flow
- есть reward loop или ясное объяснение, зачем игрок туда идёт
- есть fallback, если система временно недоступна

Если хотя бы одного пункта нет, feature должна жить:

- в roadmap
- в docs
- во внутреннем backlog

Но не в рабочей навигации игрока.

## Решения по текущим заглушкам

- `PVP Арена`: оставить в roadmap и docs, вернуть в UI только после появления страницы, серверной модели снимков и отдельного рейтинга.
- `Сезонные события`: не выдавать как activity unlock до появления event config, расписания и reward hooks.

## Риски

- Если снова вернуть «unlock без surface», игрок будет воспринимать прогрессию как сломанную.
- Если planned features отображаются как `locked`, игрок читает это как «я могу открыть», а не как «этого ещё нет».

## Правило для разработки

Для planned feature использовать только один из двух статусов:

- `roadmap only`
- `coming soon`, но без перехода и без фальшивого unlock-state
