# Anti-Cheat Baseline

## Цель

Минимально снизить доверие к клиенту без тяжёлого переписывания текущей архитектуры.

## Что теперь считается серверно-контролируемым

- CSRF-защита для всех state-changing запросов:
  - `login`
  - `register`
  - `logout`
  - `save`
  - `buy_prestige`
  - `minigame_reward`
  - `dungeon_clear`
- `prestigeMulti` в `save` больше не принимается как есть от клиента и пересчитывается на сервере из `prestige`.
- `prestigeShop` в `save` больше не принимается как произвольная карта:
  - разрешены только известные item id
  - уровни режутся по серверным `maxLevel`
- `maxOffline` больше не может быть выше серверно-допустимого лимита, вычисленного из `prestigeShop.offline_boost`.
- `prestigePoints` не могут быть выше `totalPrestigePoints`, а слишком большие скачки `totalPrestigePoints` режутся сервером.
- `accountLevel` и leaderboard продолжают вычисляться на сервере.
- Награды `minigame_reward` и `dungeon_clear` применяются через сервер с жёсткими капами.

## Что валидируется в save payload

- верхнеуровневые числовые поля приводятся к допустимым диапазонам
- карты `buildings`, `prestigeShop` нормализуются в `string -> int`
- `prestigeShop` дополнительно whitelist'ится и ограничивается серверными max level
- карты `upgrades`, `achievements`, `story` нормализуются в `string -> bool`
- `loc <= totalLoc`
- `locThisRun <= totalLoc`
- `prestigePoints <= totalPrestigePoints`
- `maxOffline` не может превышать лимит, выведенный из серверных правил prestige shop
- `lastSave` не может уходить далеко в будущее

## Что считается подозрительным и логируется

- невалидный или отсутствующий CSRF-токен
- превышение rate limit
- невалидный JSON/save payload
- аномальный скачок `prestige`
- аномальный скачок `dungeonClears`
- слишком большой скачок `totalPrestigePoints`
- завышенные уровни или неизвестные ключи в `prestigeShop`
- завышенный `maxOffline` относительно доступного оффлайн-лимита
- `prestigePoints`, выходящие за согласованный баланс с `totalPrestigePoints`
- попытка отправить награды выше серверных cap'ов
- неудачные логины
- невалидные покупки в prestige shop

Логи пишутся в `storage/logs/security.log` в формате JSON Lines.

## Что это ещё не закрывает

- сервер всё ещё принимает клиентский save blob как главный контейнер состояния
- экономическая модель idle-игры по-прежнему в основном клиентская
- нет полноценной проверки "возможности" прогресса по таймингам, LPS и истории действий
- нет отдельного event-log, из которого можно было бы воспроизводить прогресс
- сервер пока не пересчитывает весь `prestigePoints`-прогресс из истории действий, а только проверяет базовые инварианты и аномальные скачки

## Следующий уровень защиты

1. Вынести save/reward/prestige в серверные сервисы с явными DTO.
2. Хранить часть критичного прогресса не только в JSON, но и в отдельных полях/таблицах.
3. Добавить idempotency для наград активностей.
4. Ввести отдельный security/audit event stream для подозрительных прогресс-скачков.
