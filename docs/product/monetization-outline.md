# Safe Monetization Outline

## Monetization Principle

The product should monetize around expression, convenience, and support for the game's humor/theme. The main idle economy should remain readable, and prestige should remain earned through play.

The product should not position direct power sales as the main business model. That would damage the current fantasy, flatten prestige meaning, and undermine leaderboard trust.

## What Can Realistically Be Monetized

## 1. Cosmetic Themes

Low-risk options:

- alternate UI skins for idle, dungeon, and profile
- themed click-button effects
- toast/terminal visual packs
- profile badges, frames, and prestige banners
- alternate class skins in dungeon

Why this is safe:

- no direct stat advantage
- fits the humorous identity well
- works for both guests and logged-in users later

## 2. Cosmetic Narrative Packs

Low-risk options:

- extra joke story chapters in the text game
- alternate event text packs
- collectible flavor-only profile titles
- seasonal cosmetic content tied to programmer culture

Why this is safe:

- extends personality instead of power
- creates repeat novelty without touching balance

## 3. Convenience, Not Power

Acceptable convenience options:

- extra profile personalization slots later
- more visible stats history on profile
- optional session recap screen
- optional quality-of-life UI bundles such as extra dashboard views

Rule:

Convenience can reduce friction, but it should not meaningfully compress time-to-prestige or increase combat outcomes beyond what normal play provides.

## 4. Supporter / Founder Pack

A simple early monetization offer:

- unique founder badge
- exclusive cosmetic theme
- supporter title on profile/leaderboard
- optional supporter wall

Why this is realistic:

- easiest first monetization layer
- minimal design risk
- fits a small product before live-ops maturity

## 5. Rewarded Ads or Equivalent Only as Opt-In

If the project later needs ad-based monetization, the safest version is optional and capped:

- watch ad for a cosmetic token
- watch ad for a small non-stackable convenience boost with strict daily limits

This is lower priority than cosmetics/supporter packs and should not interrupt the main loop.

## What Should Not Be Monetized

The following should not be sold directly, especially early:

- direct prestige count
- direct OO bundles as the main offer
- permanent production multipliers sold for cash
- direct dungeon victories or revive sales
- leaderboard placement
- exclusive access to core progression systems
- paywalled account saving

These would create pay-to-win pressure, weaken the prestige loop, and make competition feel illegitimate.

## Caution Areas

These are possible later, but risky early:

- battle pass style structure
- premium event tracks
- convenience boosters affecting progression speed
- ad-based revival or retry mechanics in dungeon

These require analytics first, because they can distort session behavior and progression pacing.

## First Safe Experiments

## Experiment 1. Founder Pack

Contents:

- profile badge
- one exclusive UI theme
- one exclusive dungeon class skin

Why first:

- easy to explain
- low balance risk
- validates willingness to pay from core fans

## Experiment 2. Cosmetic Theme Shop

First SKU ideas:

- "Legacy Terminal"
- "Startup Neon"
- "Enterprise Beige"
- "Night Deploy"

Why second:

- directly connected to product fantasy
- repeat-purchase potential without economy damage

## Experiment 3. Seasonal Cosmetic Drop

Examples:

- April deploy disaster pack
- hackathon pack
- bug-hunt season badge set

Why third:

- tests light live-ops behavior
- creates return hooks without forcing power creep

## Suggested Monetization Order

1. Supporter pack
2. Cosmetic theme shop
3. Seasonal cosmetics
4. Very limited opt-in ads or convenience only after analytics baseline exists

## Product Guardrails

Any monetization experiment should pass these checks:

- does not sell prestige directly
- does not sell leaderboard advantage
- does not make dungeon outcomes feel bought
- does not block core content for non-paying users
- does not reduce the meaning of "rewrite from scratch"

If an offer fails one of those checks, it is too aggressive for the current product.
